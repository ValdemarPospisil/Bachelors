\chapter{Implementace}
\label{chap:implementace}

V této kapitole je detailně rozebrán samotný proces implementace navrženého řešení. Pozornost je věnována struktuře celého projektu a následně specifickým technickým výzvám spojeným s vývojem klientské aplikace v jazyce Go a úpravám systémové služby na platformě .NET.

\section{Struktura projektu a vývojové prostředí}
Jelikož se výsledný produkt skládá z několika oddělených, avšak úzce spolupracujících částí, bylo zásadní správně navrhnout strukturu repozitáře. Repozitář je koncipován jako monorepo, které zastřešuje zdrojové kódy pro všechny klientské i systémové komponenty. Tento přístup výrazně zjednodušuje správu závislostí a zajišťuje konzistentní verzování napříč celým projektem.

Hlavní rozdělení kořenového adresáře odráží oddělení jednotlivých technologických a logických domén:

\begin{itemize}
    \item \texttt{client/} -- Tato složka představuje zdrojové kódy původního grafického klienta postaveného na technologiích Electron a React. Byť není primárním předmětem této práce, jeho přítomnost v repozitáři usnadňuje sdílení prostředků.
    
    \item \texttt{cli/} -- Zde se nachází kompletní implementace nového terminálového klienta v jazyce Go.
    \begin{itemize}
        \item \texttt{cmd/} -- Obsahuje definice jednotlivých CLI příkazů využívajících framework Cobra (např. \texttt{login.go}, \texttt{connect.go}, \texttt{status.go}). Soubor \texttt{root.go} slouží jako vstupní bod pro parsování uživatelských vstupů.
        \item \texttt{internal/} -- Zapouzdřuje interní logiku aplikace, kterou nelze importovat z externích balíčků.
        \begin{itemize}
            \item \texttt{ipc/} -- Implementuje komunikační vrstvu, konkrétně klienta pro Unix Domain Sockets a definici zpráv (tzv. \textit{protocol}).
            \item \texttt{tui/} -- Zastřešuje interaktivní textové uživatelské rozhraní postavené na frameworku Bubble Tea. Každá obrazovka (např. \texttt{login/}, \texttt{connect/}) je zde oddělena do vlastní složky obsahující modely (\texttt{model.go}), zpracování událostí (\texttt{update.go}) a vykreslovací logiku (\texttt{view.go}).
        \end{itemize}
    \end{itemize}

    \item \texttt{services/} -- Obsahuje .NET projekty představující backend vrstvu, neboli systémové služby běžící na pozadí s vyššími právy.
    \begin{itemize}
        \item \texttt{CLIService/} -- Zcela nově vytvořený projekt v rámci této práce. Funguje jako dedikovaná \textit{wrapper} služba (tzv. obálka) pro CLI klienta. Hlavním úkolem \texttt{CLIService} je naslouchat na IPC socketu (\texttt{SenderReader.cs}), přijímat požadavky od frontend klienta a směrovat je pomocí komponenty \texttt{CliMessenger.cs} k příslušným výkonným vrstvám.
        \item \texttt{GoodAccess.Shared/} -- Obsahuje sdílenou doménovou logiku, kterou využívají různé části backendu. Nachází se zde klientské třídy pro komunikaci s centrálním REST API (\texttt{ApiClient.cs}) a abstraktní implementace VPN protokolů (\texttt{ProtoService.cs}, \texttt{VpnManager.cs}).
        \item \texttt{GoodAccessService/} -- Původní a hlavní jádro síťové infrastruktury (daemon). Využívá konfigurace z předchových vrstev k fyzickému sestavení a správě tunelů na daném operačním systému.
    \end{itemize}
\end{itemize}

Tato architektura je tak striktně rozdělena na takzvaného tenkého klienta (Thin Client), jenž je zodpovědný výhradně za prezentaci dat a odesílání uživatelských povelů, a robustní systémovou službu, která si ponechává komplexní aplikační logiku. Navíc obě tyto logické vrstvy (Go aplikace a .NET služby) mají vlastní nezávislé procesy pro sestavení a distribuci.

\section{Implementace systémové služby (.NET)}
Aby bylo možné efektivně zpracovávat požadavky přicházející od CLI klienta, bylo nutné infrastrukturu na straně služby patřičně rozšířit. Vývoj probíhal iterativně počínaje zajištěním bezpečného úložiště a zprovozněním lokálního komunikačního kanálu.

\subsection{Bezpečné úložiště (Secure Storage)}
Aplikace potřebuje uchovávat citlivá data jako jsou autentizační tokeny a privátní klíče. Jak bylo definováno v kapitole~\ref{sec:data_a_bezpecnost}, původní implementace pro grafické rozhraní ukládala některá data do prostoru uživatele. Jelikož je CLI klient navržen s možností trvalého spojení běžícího čistě na úrovni systému, muselo být úložiště přesunuto do bezpečného systémového adresáře (\texttt{/opt/GoodAccess/configs/DataProtection-Keys}).

Byla vytvořena třída \texttt{CliStorage} reprezentující zabezpečené úložiště. Fyzické uložení dat využívá soubory zabezpečené restriktivními přístupovými právy, čímž je zaručeno, že k souborům má přístup pouze vlastník procesu (v tomto případě uživatel \texttt{root}, pod kterým služba běží). Samotná data uvnitř souborů jsou navíc šifrována na úrovni .NET frameworku pomocí \texttt{IDataProtectionProvider}. Třída umožňuje čtení a zápis serializovaných JSON objektů do tohoto chráněného souboru.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[language=CSharp, stringstyle=\itshape]
private void WriteFile(object json)
{
    using (StreamWriter sw = File.CreateText(this._path))
    {
        sw.WriteLine(this._protector.Protect(JsonSerializer.Serialize(json)));
    }
}
\end{lstlisting}
\end{minipage}

\subsection{IPC Server (Unix Domain Sockets)}
Základním kamenem architektury je nově vytvořený modul \texttt{CLIService}. Tento modul slouží jako most mezi uživatelskými vstupy a jádrem služby. Jak bylo navrženo v kapitole~\ref{sec:navrh_ipc}, komunikace probíhá přes Unix Domain Sockets (UDS), což je na platformě Linux standardní a vysoce výkonný způsob výměny dat mezi lokálními procesy. Služba vytvoří pojmenovanou rouru (named pipe), na které asynchronně naslouchá příchozím spojením od klienta. Požadavky jsou zasílány a vraceny ve formátu JSON, což usnadňuje deserializaci dat na obou stranách.

\begin{lstlisting}[language=CSharp, stringstyle=\itshape]

    1, // Max 1 client 
    PipeTransmissionMode.Byte,
    PipeOptions.Asynchronous
);
\end{lstlisting}
\end{minipage}

\subsection{Zpracování příkazů (CliMessenger)}
Za samotné odbavování příchozích zpráv zodpovídá komponenta \texttt{CliMessenger}. Jak bylo definováno v podkapitole~\ref{sec:navrh_ipc} (včetně konkrétních JSON příkladů), každý požadavek ve formátu JSON obsahuje specifikaci příkazu (např. \texttt{login}, \texttt{connect}) a příslušné argumenty. \texttt{CliMessenger} tyto požadavky zpracovává a směruje je na specifické služby v rámci .NET backendu. Jak ukazuje následující ukázka kódu, třída pomocí konstrukce \texttt{switch} analyzuje přijatý příkaz a asynchronně volá odpovídající obslužné metody.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[language=CSharp, stringstyle=\itshape]
switch (command.ToLower())
{

    case "login":
        await HandleLogin(payload, linuxId, responseWrapper);
        break;

    case "logout":
        await HandleLogout(linuxId, responseWrapper);
        break;

\end{lstlisting}
\end{minipage}

V raných fázích vývoje, kdy ještě nebyla zcela implementována veškerá produkční logika a klientská aplikace se teprve formovala, vracela metoda \texttt{CliMessenger} provizorní, pevně definované hodnoty (tzv. hardcoded data). Tento přístup umožnil paralelní vývoj -- uživatelské rozhraní se mohlo designovat a testovat proti konzistentnímu API bez čekání na dokončení komplexní aplikační logiky. Postupem času byly tyto provizorní odpovědi nahrazovány reálným napojením na síťové a autentizační subsystémy.

\subsection{Životní cyklus a integrace se systemd}
Pro zajištění běhu služby na pozadí a správnou instalaci na Linuxu byl využit modul \texttt{Microsoft.\allowbreak Extensions.\allowbreak Hosting.\allowbreak Systemd} (~\ref{sec:technologie}). Díky tomuto modulu se celá aplikace může chovat jako nativní \texttt{systemd} služba. Definice \texttt{goodaccess-cli.service} zajižduje automatické spuštění po startu systému a \textit{graceful shutdown} proces pro bezpečné odpojení VPN před vypnutím. Následující ukázka kódu z konfigurační třídy \texttt{Program.cs} demonstruje inicializaci hostitele, kde metoda \texttt{UseSystemd()} registruje životní cyklus služby a zároveň probíhá konfigurace \texttt{DataProtection} API z předchozí podkapitoly a registrace hlavní pracovní třídy \texttt{Worker}, která obstarává chod aplikace v pozadí.

\section{Pokročilé funkce a technické výzvy}
Během integrace stěžejních funkčních celků do architektury se objevilo několik netriviálních technických výzev, které vyžadovaly hlubší analýzu a návrh specializovaných řešení.

\subsection{Správa VPN spojení (OpenVPN)}
Samotné vytvoření šifrovaného tunelu skrze protokol OpenVPN těží z již existující architektury modulu \texttt{ProtoService}, který je nasazen na ostatních platformách. Pro potřeby CLI klienta tak stačilo mapovat požadavky z UDS rozhraní do podoby interních struktur sítě a volat sdílenou aplikační logiku. Modul automaticky vygeneruje odpovídající konfiguraci, sestaví spojení a na pozadí monitoruje stabilitu relace.

\subsection{Persistentní relace a vícero uživatelů}
Jednou z definovaných funkčností v rámci funkčních požadavků (kapitola~\ref{sec:funkcni_pozadavky}) byla možnost navázání persistentního (trvalého) spojení, kdy VPN zůstává aktivní i po odhlášení aktuálního systémového uživatele nebo po restartu zařízení. Tento požadavek si vyžádal řešení problému týkajícího se izolace více Linuxových uživatelů. Jelikož je sestavené VPN spojení systémového charakteru (routování přes rozhraní tunelu ovlivňuje globální směrovací tabulky stroje), mohlo by dojít k situaci, kdy jeden uživatel sestaví persistentní spojení a jiný uživatel po přihlášení nemá oprávnění jej modifikovat či ukončit, přestože je jeho síťový provoz rovněž šifrován. Z toho důvodu bylo nutné obohatit komunikační protokol IPC o explicitní předávání systémového kontextu a identifikaci uživatele, který požadavek vznáší. Pokud je aktivní persistentní tunel spuštěný jiným uživatelem a nejedná se o autorizovanou operaci, je akce zamítnuta na úrovni služby (Obrázek~\ref{fig:another_user_connected}). Administrátor pak musí relaci manuálně ukončit přes příkaz vyžadující superuživatelská práva voláním \texttt{sudo ga-cli disconnect}.

\subsection{Implementace protokolu WireGuard}
Moderní protokol WireGuard představoval v kontextu architektury významnou výzvu, jelikož práce zahrnovala implementaci samotného agenta (sestavování sítě) cíleně pouze pro prostředí Linux s využitím statických konfigurací. Na rozdíl od uceleného řízení (životní cyklus přes operační systém, dynamické doporučování gateway, automatické znovupřipojení), které přesahuje rámec této bakalářské práce a je paralelně vyvíjeno ostatními členy týmu na různých platformách, se tato konkrétní implementace zaměřuje primárně na fundamentální logiku navázání komunikace přes nativní systémové nástroje (\texttt{ip link}, \texttt{wg}). Tyto operace jsou vloženy do kontextu služeb \texttt{ProtoService} a tvoří základ budoucí robustní síťové logiky.

\subsection{Vylepšení uživatelské přívětivosti (UX)}
S cílem maximalizovat komfort koncových uživatelů při interakci v terminálu byl klient postupně doplňován o podpůrné funkce a vizuální prvky definované v kapitole~\ref{sec:vizualni_styl}. Byly implementovány kontextové nápovědy (tzv. \textit{hints}), které uživateli po dokončení operace nebo při kontrole stavu navrhují další logický krok. Například, je-li uživatel odhlášen, příkaz \texttt{status} nejen zobrazí aktuální stav, ale zároveň nabídne spuštění příkazu \texttt{ga-cli login}. Dalším důležitým UX prvkem je okamžitá vizuální odezva u déletrvajících operací (např. sestavování VPN spojení), jež byla realizována pomocí animovaných načítacích elementů (spinnerů).

Důležitým přepínačem (flag) je plná podpora pro strojově čitelné formátování výstupů prostřednictvím \texttt{--json}. Tento flag zajišťuje, že aplikace nebude vracet interaktivní textové uživatelské rozhraní ani barevně formátovaný text, ale striktně strukturovaný JSON výstup. Tato funkcionalita je klíčová pro případnou integraci CLI nástroje do CI/CD řetězců (pipelines) a automatizačních skriptů, kde je vyžadováno bezobslužné řízení celého procesu připojení a zpracování jeho výsledků.

\section{Rozdíly ve správě stavu: GUI vs. CLI}
\label{sec:gui_vs_cli_state}
Jedním z nejvýznamnějších architektonických rozdílů mezi grafickým klientem (GUI) a klientem v příkazovém řádku (CLI) je způsob správy stavu a ošetření uživatelských akcí. V GUI aplikaci je běžnou praxí vizuálně omezit akce, které neodpovídají aktuálnímu stavu. Například tlačítko „Připojit“ je deaktivováno nebo skryto, dokud se uživatel úspěšně nepřihlásí. Uživatel tak nemá možnost vyvolat neplatný stav pouhým kliknutím.

Naproti tomu CLI prostředí je ze své podstaty bezstavové z pohledu samotného vstupu. Uživatel může kdykoliv napsat jakýkoliv příkaz nezávisle na aktuálním stavu aplikace na pozadí. Proto je nezbytné, aby CLI klient na každý takový příkaz reagoval předvídatelně a v případě neplatného stavu poskytl jasnou chybovou hlášku s návodem k nápravě. Například, pokusí-li se nepřihlášený uživatel o připojení k VPN (\texttt{ga-cli connect}), aplikace musí požadavek zachytit a korektně odmítnout s výzvou k přihlášení.

Tato odlišnost si vyžádala pečlivé zmapování všech možných kombinací příkazů a stavů aplikace. Následující tabulka ukazuje, jak se různé příkazy chovají v různých stavech služby.

\section{Distribuce a automatizace aktualizací}
\label{sec:impl_distribuce}

Aby bylo dosaženo plné integrace do linuxového ekosystému, jak bylo navrženo v kapitole \ref{sec:distribuce_aktualizace}, bylo nutné implementovat proces sestavení distribučních balíčků a mechanismus pro detekci nových verzí.

\subsection{Příprava distribučních balíčků (.deb, .rpm)}
Pro automatizaci procesu balíčkování byl obsah a metadata balíčku deklarativně popsán v jediném konfiguračním souboru (teoretický rozbor balíčkovacích systémů viz sekce \ref{sec:distribuce}). Tímto způsobem bylo možné z jediného zdroje generovat balíčky pro rodinu Debian (\texttt{.deb}) i Red Hat (\texttt{.rpm}).

Klíčovou součástí balíčků jsou takzvané \textit{maintainer scripts} (viz sekce \ref{sec:distribuce}), které zajišťují správnou registraci a spuštění systémové služby. V rámci balíčku pro GoodAccess CLI byly implementovány skripty \texttt{postinst} (pro Debian) a \texttt{post} (pro RPM), které po instalaci:
\begin{enumerate}
    \item Reloadují konfiguraci \texttt{systemd} (\texttt{systemctl daemon-reload}).
    \item Aktivují a spustí službu \texttt{goodaccess-cli.service}.
    \item Nastaví restriktivní oprávnění (\texttt{chmod 700}) pro hlavní binární soubor klienta, aby se zamezilo neautorizovanému spuštění.
\end{enumerate}

\subsection{Implementace detekce aktualizací}
Jak bylo navrženo v kapitole \ref{sec:distribuce_aktualizace}, aplikace se spoléhá na proaktivní detekci nových verzí. Tato logika byla implementována v rámci komunikace se službou. Služba při každém požadavku na zobrazení stavu (\texttt{ga-cli status}) asynchronně porovnává lokální verzi s verzí dostupnou na centrálním API.

Pokud je zjištěna novější verze, je v odpovědi ze služby nastaven příznak \texttt{UpdateAvailable}. Klientská aplikace v Go následně tuto informaci interpretuje a zobrazí uživateli upozornění přímo v terminálu.

\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[language=Go, stringstyle=\itshape]
// returned by the background service.
type AppStateResponse struct {
	IsLoggedIn             bool   `json:"isLoggedIn"`
	IsConnected            bool   `json:"isConnected"`
	UserName               string `json:"userName"`
	IsAnotherUserConnected bool   `json:"isAnotherUserConnected"`

	// UpdateAvailable is set to true if the service detects 
	// a newer version on the central API.
	UpdateAvailable        bool   `json:"updateAvailable"`
}
\end{lstlisting}
\end{minipage}

Tento přístup kombinuje bezpečnost nativní správy balíčků s uživatelským komfortem okamžité informovanosti o dostupných vylepšeních.
